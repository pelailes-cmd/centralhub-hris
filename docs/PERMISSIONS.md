# Permission matrix

Job classification, position, department, reporting relationship, functional role, and access scope are separate records. Changing a job title or classification never grants permissions. The following templates are applied only through an explicit authorized assignment. Runtime access checks use the resulting permission-grant rows and the current organization records.

## Baseline for every active employee

- Own work profile and permitted private personal-information updates (personal email, address, emergency contact). Work titles, department, reporting manager, status, and roles remain administrator-controlled.
- Own clock-in/out, attendance history, schedules, correction requests, leave balances, leave requests, and overtime requests.
- Own published payslips; own drafts and other employees’ pay are not included.
- Own personnel documents, tasks, onboarding/cleaning checklists, training, assigned reviews, feedback, notifications, and acknowledgements.
- Company announcements and company policies applicable to their department.
- Bank, government, medical, disciplinary, and identity categories still require their own explicit permission, including when the record belongs to the employee.

## Scope rules

| Scope               | Record match                                                                                                                       |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Own                 | Target employee is the employee linked to the authenticated account.                                                               |
| Direct reports      | Target employee’s stored manager ID equals the authenticated employee ID. This does not include indirect reports.                  |
| Assigned team       | Target employee’s primary team matches the specific team ID on the grant.                                                          |
| Assigned department | Target employee’s department matches the specific department ID on the grant. Department ancestry does not imply inherited access. |
| Company             | All eligible records within this single-company deployment.                                                                        |

For multiple assigned teams or departments, add one scoped assignment per team or department. Department-scoped planning uses the plan’s target department. Organization governance and permission-grant administration require company-scope permission. Account operations are separately authorized from HR record access.

## Combinations

- **Specialist + HR Officer, People & Culture department:** self-service plus the HR Officer grants for employees in that department. No automatic payroll, medical, disciplinary, bank, government-ID, or identity-file access.
- **Managerial, Engineering team + Payroll Administrator, Finance department:** team directory/attendance/approval responsibilities for Engineering, plus payroll responsibilities only for employees in the explicitly assigned Finance department. Final approvals still need an approval-route assignment.
- **Owner + Technical Administrator, company:** governance and account operations. Confidential HR and payroll still require explicit additional grants. This is the first-admin bootstrap combination.

## Approval authority

A decision requires an active account/session, required MFA, a matching current permission and scope, and the explicit approver or valid delegate assignment. Requesters cannot approve their own requests. The initial leave.approve capability covers assigned leave and overtime decisions; attendance corrections use attendance.manage; headcount plans use planning.manage. Supervisor recommendations do not finalize a request. Reviewer assignments authorize review feedback only for the assigned employee.

Temporary leave/correction delegates must hold the relevant scoped permission, and their stored delegation period must still be valid. Request records retain the approver and delegate selected at submission. A route change does not silently rewrite existing requests.

## Field and document boundaries

| Data                                           | Read boundary                                                                               | Write boundary                                                          |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Work directory                                 | Own record, employees.read within scope, or applicable assigned-review context              | employees.manage for both current and destination scope                 |
| Personal contact/address/emergency information | Own record or private.read within scope; audited RPC                                        | Own permitted fields or private.write within scope; audited RPC         |
| Payslips/compensation                          | Own published statement or explicit payroll authorization; audited RPC, no raw table SELECT | payroll.manage; create/import drafts, explicit publication              |
| Company documents                              | Active employees in the applicable company/department audience                              | documents.manage at the company/department audience                     |
| Personnel documents                            | Own file or documents.read within scope                                                     | documents.manage within scope                                           |
| Bank details                                   | sensitive.bank.read within scope                                                            | sensitive.bank.write within scope                                       |
| Government identifiers                         | sensitive.government.read within scope                                                      | sensitive.government.write within scope                                 |
| Medical records                                | sensitive.medical.read within scope                                                         | sensitive.medical.write within scope                                    |
| Disciplinary records                           | sensitive.disciplinary.read within scope                                                    | sensitive.disciplinary.write within scope                               |
| Identity files                                 | sensitive.identity.read within scope                                                        | sensitive.identity.write within scope                                   |
| Review feedback                                | Employee, assigned reviewer, or scoped performance.read; audited RPC                        | Employee reflection or assigned reviewer feedback; HR assigns reviewers |
| Accounts                                       | Account/access administration only; employee work identity for account operations           | accounts.manage; no self-suspension or self-deactivation                |
| Permission grants                              | Own grants or access.manage                                                                 | access.manage; no login/registration role fields                        |
| Audit events                                   | Company-scope audit.read                                                                    | Internal audited functions only                                         |

All elevated permission grants require MFA. The role label itself is not checked for authorization. Removing a grant changes access on the next request. Deactivation, logout, expiration, or revocation invalidates the application session even when the client still holds a previously issued JWT. Raw sensitive tables, Auth tickets, rate-limit keys, and storage objects are inaccessible through ordinary authenticated/anonymous API calls.
